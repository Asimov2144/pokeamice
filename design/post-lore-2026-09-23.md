# 每篇文章的图鉴条目（post lore）

App 的全域图鉴机要能对着一篇资料说话：这篇点名了哪几只宝可梦、哪几部作品、哪个地方、哪个人，
读到第几段有什么可说的，跟别的哪一篇是同一件事。以前这些是 App 拿标题和正文现猜的
（`globalDex/docsDex.ts` 的 `pokemonOfPost()` 扫标题、`placeLinks.ts` 那张 17 条的人工表）。
现在由 docs 侧在构建流程里生成，做法照旅图的 `dex-lore`：机器写、带出处、可手改、只有改动的篇目重跑。

2026-09-23 先按 50 篇试点（访谈 31、博客 13、扫描 6、站内长文 3），形状定下来再铺全量。

## 生成

```bash
python tools/sync-lore-tables.py            # 两张对照表（宝可梦写法、旅图地点）从 App / platform 抄进来
python tools/build-post-lore.py --pilot 50  # 规则 + DeepSeek，写 data/post_lore/<id>.json
python tools/build-post-lore.py --pilot 50 --relations   # 第二趟：文章之间的关系
python tools/export-docs-archive.py         # 并进 assets/data/app/
```

- `--no-llm` 只跑规则（不花钱）；`--force` 忽略缓存；`--only <id>…` / `--all`。
- 缓存在 `data/cache_lore/<id>.json`，键是「给模型看的那段材料」的哈希——正文没变就不再问。
- 单篇原件 `data/post_lore/<id>.json` 可以手改；把 `"edited": true` 写上，以后重跑就不覆盖它。
- 汇总 `_data/post_lore.yml`（按 `_posts` 的文件名索引）给文章页的「本篇提到」一栏用。

## 两张对照表

`data/lore_tables/` 里放的是抄过来的副本，不是依赖：

| 文件 | 来自 | 内容 |
|---|---|---|
| `pokemon_names.json` | `Pokeamice_app/src/pokemonSprites.ts` | 3249 个写法（中/日/英、地方形态）→ 全国图鉴号；图鉴号 → 中文名 |
| `tour_places.json` | `pokeamice-platform/event/public/tour-places.json` | 714 条里去掉 489 个井盖，剩 224 处：宝可梦中心、GF 旧址、会场、体育馆、店 |

两边的 id 就是 join 键。表里记了抄的日期，每条 lore 也记了自己当时对的是哪个版本
（`sources.pokemon_names` / `sources.tour_places`），表更新了但没重跑的篇目一眼看得出来。
`tools/sync-lore-tables.py --check` 只报告新旧，不写。

## 记录长什么样

```jsonc
{
  "id": "interview-wedge-ishihara-pokemon-disney",
  "stem": "2010-05-12-interview-wedge-ishihara-pokemon-disney",
  "kind": "interview",
  "body": { "kind": "segments", "n": 246 },
  "facets": {
    "pokemon": [{ "name": "皮卡丘", "ndex": 25, "seg": [190, 199, 205], "as": ["皮卡丘"], "via": "body" }],
    "works":   [{ "name": "宝可梦 红·绿", "slug": "red-green", "seg": [28, 76], "via": "entities" }],
    "people":  [{ "name": "石原恒和", "slug": "ishihara-tsunekazu", "role": "speaker", "seg": [8, 12] }],
    "places":  [{ "name": "六本木新城", "id": null, "entity": null, "category": null,
                  "world": "real", "what": "宝可梦公司总部", "seg": [7], "via": "llm" }]
  },
  "observations": [
    { "seg": 1, "anchor": 2, "text": "《宝可梦》1996年发售，至今14年，全球累计市场3万亿日元" }
  ],
  "relations": [
    { "id": "interview-gamer-pokemon-press-conference-2018", "kind": "same-occasion",
      "label": "同一件事的另一种说法", "why": "同为2018年5月30日新作发布会报道" }
  ],
  "sources": { "pokemon_names": "2026-09-23", "tour_places": "2026-09-23", "model": "deepseek-chat" },
  "edited": false
}
```

几个要紧的约定：

- **`seg` 就是 App 的段号**：`posts/<id>.json` 里 `body.segments[].n` 那个号，
  `docs:post/<id>?s=<n>` 直接跳得到。生成时调的就是导出器自己的 `normalize_parallel` /
  `normalize_scan`，不是另算一套。
- **`anchor` 是 docs 网页上的锚点号**（`#segment-N`），和 `seg` 不是一回事（网页按
  `parallel_items` 原序号排，导出器把空段滤掉了）。扫描件的版面按页重排，对不上，`anchor` 就不给。
- **地点分两层**，和 App 那张人工表一致：`id` 是某一处店址，`entity` 是这家店本身
  （文章写「宝可梦中心东京」给的是 `entity: pokemon_center_tokyo`，由 App 按发表日期落到当时的店址）。
  两个都为空就是旅图上没有的地方，只有名字，当文字显示即可。
- **`world`**：`real` 是现实地点，`game` 是游戏与动画里的地方（「合众地区」「华蓝市」），
  后者不要往旅图上连。
- **`via`**：`entities` 来自前言（编者写的）、`body`/`gazetteer`/`tag`/`title` 是规则扫出来的、
  `llm` 是模型补的。要更保守就只信前三种。
- **`relations.kind`** 只有五种：`same-occasion`（同一场的另一篇报道）、`continues`（同一系列前后篇）、
  `responds`（后来回应）、`corrects`（后来更正）、`background`（读懂这篇需要的背景）。
  候选是按共同人物、共同作品、同出处、年份相近选出来的最多 8 篇，模型只留说得出理由的。
  `background` 最松，用之前值得人眼过一遍。

## App 拿到的形状

`tools/export-docs-archive.py` 把同一份记录并进两处（`schema_version` 没动，还是 3，老版本忽略即可）：

- `index.json` 的每行多一个 **`lore`**：`{ "dex": [25, 251], "places": [{id|entity|name}], "obs": 2, "rel": 1 }`
  ——前台挑卡片、按宝可梦找文章够用，索引不会被撑大。
- `posts/<id>.json` 多一个 **`lore`**：`facets` / `observations` / `relations` / `sources` / `built` / `edited`，
  外加导出时算好的 **`by_seg`**：

  ```jsonc
  "by_seg": { "190": { "dex": [25] }, "7": { "places": ["六本木新城"] }, "1": { "obs": 0 } }
  ```

  读者摘了一段（`docsNotes` 的 `note.segment`）或写了评注，App 拿段号往 `by_seg` 里一查就知道
  这一段说的是谁、哪只、哪儿，`obs` 是 `observations` 的下标——图鉴机接话、事后提醒都用这个。
- `manifest.json` 的 `counts.lore` 记了铺了多少篇。

### 可以替掉的两处

- `globalDex/docsDex.ts` 的 `pokemonOfPost()`：有 `lore.dex` 就用它（已经是图鉴号，不必再猜写法），
  没有再退回现在的标题扫描。
- `placeLinks.ts`：那张人工表仍是准的（写过原文、带「为什么挂在这儿」），lore 的 `places` 是补充——
  人工表没有的篇目才用，且只连 `id` / `entity` 有值、`world: real` 的。

## 还没做的

- 只铺了 50 篇。全量 1152 篇约 3–4 小时、DeepSeek 几美元；缓存在，分批跑也行。
- 地点对上旅图 id 的只有 1 处——文章里的「六本木新城」「下北泽」旅图上本来就没有。
  要提高命中，得给 gazetteer 补一批「文章会提到的地方」，或者照 App 的 `areas` 那样按标签匹配一片。
- 读者评注（不是摘录）的识别还没做：现在能给的是段号 → 这一段有什么，评注本身的归类要等 App 那边定形状。

## 2026-09-25：全量铺完，App 已接上

试点 50 篇 → **全部 1,172 篇**（访谈 416 · 官方博客 710 · 扫描 39 · 站内长文 7）：
**2,268 条观察**（821 条带网页锚点）、**1,635 条关系**、点名 **574 种宝可梦**、
**142 处**地点连得上旅图或 App 的对照表（24 个去处）。跑法照旧，两趟都走缓存。

这一轮改的：

- **店址 vs 店**：不带括号的店名给 `entity`（这家店），只有「（松坂屋二代店址）」这种
  带括号的写法给某一处的 `id`——2012 年的专栏说「宝可梦中心名古屋」不该指向 2024 年的新址。
  连到某一处而文章年份不在营业期内时标 `when: before | after`。
- **`data/lore_tables/places_extra.yml`**：手写的地名补充（旅图上没有、或对不上的）。
  `place / entity / area / category` 是 App 侧的键，`by_year` 分时期（GAME FREAK 的办公室
  2007 年前下北泽、2008–2019 胡萝卜塔、2020 起神田广场），`scan: false` 的词不扫正文、
  只在模型点名时认（公司名、泛称满篇都是）。
- **`scale: spot | area`**：「东京」「日本」「纽约」是背景地区，排在具体地点后面。
- **`lore.guess`**（目录行）：这一行里只有模型点出来的那几个图鉴号（`via: llm`）。
  App 的证据闸拿它把推测排除在「这篇说到的」之外——1,082 行里 83 行有。
- 关系只留得下真连得上的：网页那份按 `git ls-files` 滤掉指向未提交帖子的，
  App 那份按本次导出里有的 id 滤。
- 两个写盘处都改成临时文件 + 原子改名 + 退避重试（连写上千文件时 Windows 偶发 Errno 22）。

**App 侧（2026-09-25 验过线上数据）**：`pokemonOfPost()` 已改用 `lore.facets.pokemon`
（带段号），目录行按 `guess` 走证据闸；阅读器新增一条观察——读者摘录 / 笔记的段号往
`by_seg` 一查，说得出那一段点名了谁 / 哪只 / 哪儿，核对引正文原句（App `070b9e3`）。
剩下的口子：旅图缺早期店址（横滨 2018 起、东北 / 福冈 / 广岛 2025 起），所以更早的文章
只能标 `when: before`；约 460 个未命中的地名基本是旅行见闻，不打算连点位。
